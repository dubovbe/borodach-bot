# Команда проекта

Дата: 2026-11-06. Выбраны обязанности и стартовые модели разработчика и проверяющего. Все 283 исходные роли остаются установленными; это описание ограничивает использование ролей в данном проекте.

## Основной состав

| Роль Agency Agents | Обязанности в проекте | Ограничения |
| --- | --- | --- |
| Agents Orchestrator | Основной агент чата: сохраняет согласованные требования, оценивает сложность, выдаёт небольшие задания, проверяет результат, ведёт историю Git и обсуждает следующий этап | Не запускает весь автономный конвейер из исходного профиля; не создаёт отдельного оркестратора поверх основного агента |
| Backend Architect | Работник для конкретной задачи по TypeScript, PostgreSQL, правилам записи и Telegram webhook | Один бот на Workers; без микросервисов, Redis, Kubernetes, платных сервисов и требований к промышленному масштабу из примеров профиля |
| Code Reviewer | Независимое ревью законченного изменения: корректность, доступ, пересечения броней, повторы событий, миграции и необходимые тесты | Только конкретный diff и связанные файлы; не переписывает код самостоятельно и не проводит полный аудит проекта на каждом этапе |

Основной агент также может выполнить маленькую задачу самостоятельно. Отдельный работник оправдан ограниченным объёмом задания или независимостью проверки, а не наличием роли в каталоге. Порядок реализации и обязательные проверки уточняются в согласованном плане Superpowers; этот документ их не заменяет.

## Специалисты по необходимости

- DevOps Automator: публикация Workers, настройка Neon, CI, проверка квот и восстановления; без дополнительных инфраструктурных платформ из примеров роли.
- API Tester: адресные проверки webhook, повторной доставки, отказов Telegram/Neon и конкурентных запросов. Не вводит произвольные требования «95% покрытия», «200 мс» и нагрузку «10x» из общей инструкции.
- Application Security Engineer: проверка прав ролей, контакта телефона, webhook-секрета и приглашений перед публикацией. Объём — конкретные пути доступа, не корпоративная программа безопасности.

Эти специалисты не входят в постоянно работающий состав и не запускаются автоматически вместе с основной тройкой. Senior Developer не выбран: исходная инструкция ориентирована на Laravel/Livewire, наш стек — TypeScript.

## Как передаём работу

Каждое задание содержит: точную цель, выбранную роль и путь к её инструкции, нужный раздел спецификации, разрешённые файлы, критерии проверки и ожидаемый короткий отчёт. Для изолированного работника указывать абсолютный путь проекта и требовать прочитать AGENTS.md: текущая рабочая директория чата — C:/codex_projects.

Работник читает установленный TOML и применяет поле developer_instructions в пределах задания. Согласованная спецификация, ограничения задачи и инструкции проекта сохраняются; общие примеры профиля не становятся требованиями проекта. Работник не меняет модель, не публикует изменения и не запускает своих работников. Основной агент проверяет diff и результаты, затем делает коммит и публикацию согласованного этапа.

Передавать короткий контекст, не всю переписку. Не запускать несколько работников на одних файлах. Не устраивать повторное ревью без новых изменений или нерешённого замечания. Использовать ограниченный объём ответа. При ошибке сначала конкретная диагностика, а не автоматический цикл повторов из исходного профиля оркестратора.

## Фактический способ запуска

В текущем чате инструмент spawn_agent поддерживает изолированный контекст и текст задачи, но не параметр agent_type для выбора установленной роли. Поэтому используем явную загрузку TOML-файла в задании субагента. Установка файлов и такой запуск не доказывают автоматическое обнаружение именованных ролей клиентом Codex.

Пробный запуск Code Reviewer выполнен 2026-11-06 в изолированном контексте: субагент прочитал установленный файл, вернул имя роли и SHA-256-префикс `40e32a1188bb`, проверил код аудита и отчёт, не изменял файлы и не создавал вложенных агентов. Существенных преувеличений в отчёте не нашёл; отдельно указал, что проверка выполнена чтением, а не повторным запуском записывающего манифест скрипта. Основной агент сверяет префикс с установленным файлом перед фиксацией результата. Это доказывает выполнение задания с явно загруженной инструкцией, не автоматический выбор роли. При появлении нативного выбора его нужно проверить отдельно; не имитировать отсутствующий параметр и не обещать, что перезапуск приложения изменит схему инструментов.

## Модели и оценка сложности

Модель — отдельная настройка, роль — набор инструкций. Роль «архитектор» сама по себе не делает модель мощнее. Пользователь согласовал стартовые настройки 2026-11-06:

| Участник | Настройка |
| --- | --- |
| Оркестратор | Текущий чат; агент самостоятельно модель не переключает |
| Разработчик (Backend Architect) | GPT-6.1 Sol, Medium |
| Проверяющий (Code Reviewer) | GPT-6.1 Sol, Medium |

Для двух работников передавать в spawn_agent явные model="gpt-6.1-sol", reasoning_effort="medium", fork_turns="none". Их роль определяется прочитанной инструкцией, а не названием модели. Глобальные исходные профили Agency Agents остаются без изменений, поэтому сохранённые контрольные суммы продолжают соответствовать установленным файлам. Это правила запусков в данном проекте, не глобальная настройка всех чатов. Для дополнительных специалистов модель оценивается отдельно перед запуском.

До каждого этапа: сложность низкая/средняя/высокая, достаточно ли текущей модели, причина рекомендации усиления. При необходимости более сильной модели основной агент предупреждает до работы и согласовывает изменение для конкретной задачи. Пробный запуск Code Reviewer ранее выполнялся с наследованием текущей модели, до согласования явных настроек; он не считается проверкой настройки маршрутизации GPT-6.1 Sol + Medium. Явные параметры будут проверены при следующей содержательной задаче без лишнего пробного запуска.

Настройка скорости субагентов не доступна в инструменте запуска. Не гарантировать экономию лимитов только за счёт делегирования. Основные способы экономии: маленькие задания, короткий контекст, подходящий объём проверок и отсутствие лишних параллельных работников.

Для этапа 2 отдельно согласовано: разработчик Sol Medium, проверяющий Sol High. Перед запуском этапа пользователь также сообщил, что выставил Sol High в основном чате. Изменение не распространяется автоматически на другие этапы и не является изменением глобальных файлов ролей Agency Agents.

Для этапа 3 сохраняется распределение: разработчик Sol Medium, независимый проверяющий Sol High; основной чат пользователь оставил на Sol High. Изменения ограничены этапом3.

Для этапа4 продолжаем Sol Medium для разработчика и Sol High для проверяющего. Инструмент spawn_agent теперь поддерживает native agent_type; в этом этапе выбраны Backend Architect и Code Reviewer. Это изменение доступной схемы инструмента, не переустановка или изменение глобальных файлов Agency Agents. Предыдущие результаты ручной загрузки TOML остаются историческими фактами.

Для этапа5 сохраняется Sol Medium для разработчика и Sol High для независимого проверяющего. Используются нативные Backend Architect/Code Reviewer; новые этапы не начинаются автоматически.

Для согласованного этапа 6 продолжаем Backend Architect Sol Medium и Code Reviewer Sol High. Проверяющий сначала проверил стыки форм, прав, очереди и решений мастера; тот же проверяющий затем проверит готовый этап. Разработчик не запускает вложенную команду. Основной агент отвечает за собственные проверки, GitHub и ручную проверку тестового бота.

Для этапа 7 сохраняется та же команда и разделение ответственности. Preflight проверяет повторную отправку, пересчёт времени и отмену; дальнейшее ревью использует готовый diff. Ресурсы и рабочие тестовые записи сохраняются, постоянно работающая команда не запускается.

Полный SQL-набор проверяется в GitHub CI с PostgreSQL 17. В Neon проверяем изменённые сценарии, ограничения и необходимую диагностику задержек; полный удалённый прогон повторяем при обоснованной необходимости. После исправления запускаем затронутые проверки. Результаты и ограничения сохраняем в отчёте, чтобы продолжение после перерыва не запускало завершённую работу заново.

Для согласованного этапа 8 продолжаем Backend Architect Sol Medium и Code Reviewer Sol High. Независимый preflight проверяет согласие противоположной стороны, версии визита/переноса, блокировки, телефонную привязку и перепланирование напоминаний; тот же проверяющий затем получает готовый diff. Реализация ограничена переносами и минимальными меню для них.
