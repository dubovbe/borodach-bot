# Эксплуатация и восстановление

Статус: скрипты и восстановление синтетической базы проверены на Windows/PostgreSQL 18.6; полный CI Windows/Linux пройден на [этапе 11](stage-11-validation-recovery.md). Регулярные копии действующей схемы и планировщик пока не настроены. Ручная приёмка результатов и статистики этапа 10 завершена 9 ноября на обоих аккаунтах.

## Три роли

Клиент входит по общей или персональной ссылке, выбирает услуги/время, подтверждает собственный контакт и отправляет заявку. Подтверждение приходит после решения мастера. В «Моих записях» доступны свои записи, отмена и запрос переноса; в настройках — телефон и время напоминания.

Мастер по приглашению получает своё «Рабочее место»: день/неделя, ожидающие заявки, ручная запись и действия со своими визитами. Ручная запись подтверждается сразу. Отмена мастером требует причины; результат «Завершён» или «Не явился» отмечается после времени начала. Текст причины отмены не заменяет отметку результата.

Администратор управляет услугами, рангами, тарифами, мастерами и графиком через «Управление». В рабочем месте и статистике доступен выбор мастера. Исправление результата требует причины и сохраняется в истории. Изменение тарифа не меняет снимки существующих визитов; конфликтующее изменение графика отклоняется.

## Проверка доступности

`/health` проверяет доступность HTTP-обработчика без запроса базы и раскрытия настроек. Успешный health не подтверждает работу всей записи, Telegram-доставки или расход бесплатных квот. Для проверки записи используются отдельные вымышленные визиты и реальные действия тестовых аккаунтов.

Служебный smoke выполняет только проверки доступности/секрета/невалидного JSON; он не создаёт заявки и не отправляет сообщения. Команда регистрации webhook применяется отдельно по явному решению оператора, сохраняя ожидающие Telegram-обновления.

Node 24 должен быть доступен в PATH. При уже настроенном окружении `SMOKE_URL` содержит корневой HTTPS-адрес Worker без query/fragment, а необязательный `WEBHOOK_SECRET` включает проверку отказа невалидному JSON:

```powershell
node scripts/smoke.ts
```

Ожидаются `ok:true`, `health:true`, `unauthorized:true` и при переданном секрете `malformed:true`. Для отдельной регистрации webhook задать `BOT_TOKEN`, `WEBHOOK_SECRET`, `WEBHOOK_URL` (полный HTTPS-путь `/webhook`) и запустить `node scripts/set-webhook.ts`. Команда сохраняет ожидающие обновления, принимает message/callback_query и ограничивает подключения одним. Секреты задаются локально и не вставляются в чат или сохранённую историю команд.

## Резервные копии

Копия содержит одну явно выбранную схему приложения: справочники, визиты и снимки, контакты/роли приложения, историю миграций, обработанные события, формы, кнопки, очереди и попытки доставки. Глобальные роли PostgreSQL и остальные схемы общей базы в неё не входят.

Требуются выбранный пользователем зашифрованный каталог вне Git, совместимые утилиты PostgreSQL и отдельные параметры подключения. Шифрование не следует из имени каталога или правила `.gitignore`. Рабочая копия содержит данные клиентов и хранится приватно. Пароли передаются дочерним утилитам через окружение, а не аргументы команд или вывод.

Сохраняются семь последних успешных копий выбранного источника/схемы. Неудачная попытка не обновляет возраст последней успешной копии. Ежедневная задача Windows выполняется на включённом компьютере; пропущенный запуск требует StartWhenAvailable. Это не круглосуточная облачная гарантия. Каталог и настоящая задача пока не настроены.

Команды не загружают `.env` автоматически и не используют рабочую `DATABASE_URL`. Оператор заранее задаёт отдельное окружение:

| Переменная | Значение |
| --- | --- |
| `BACKUP_DATABASE_URL` | Прямое подключение PostgreSQL к источнику, без pooler и `options/search_path`; пароль остаётся локальным |
| `BACKUP_SCHEMA` | Одна существующая схема приложения |
| `BACKUP_DIR` | Абсолютный существующий обычный каталог вне Git, без символьных ссылок; для данных клиентов — выбранный зашифрованный том |
| `PG_BIN_DIR` | Необязательный абсолютный каталог psql/pg_dump/pg_restore версии 18; иначе используются PATH |
| `PG_SSL_ROOT_CERT` | Необязательный абсолютный путь к доверенному публичному PEM CA, если системного хранилища недостаточно |
| `NODE_BIN` | Необязательный путь Node 24 для PowerShell-обёрток |
| `SOURCE_CODE_SHA` | Необязательный полный 40-символьный SHA совместимого кода |

Удалённое подключение всегда проверяет сертификат и имя сервера (`verify-full`); `sslmode=disable` разрешён только для loopback. Подключение, имя схемы, каталог и версии проверяются до записи. Специальный `SYNTHETIC_TEST=true` нужен только изолированному упражнению с контролируемыми именами тестовых БД, его не используют для настоящих данных.

```powershell
pwsh -NoProfile -File scripts/backup.ps1
npm.cmd run ops:status
```

Backup: код 0 и `backup:true,retention:true` — успешная копия и очистка; код 1 — ошибка; код 2 и `backup:true,retention:false` — архив опубликован, но старые копии удалить не удалось. При коде 2 проверить права/место и оповещение планировщика; успешный архив не удалять. Status сообщает `available` и `ageSeconds`; отсутствие копии — `available:false,ageSeconds:null`. Контролировать возраст отдельно от кода завершения задания.

Архив `.dump` считается успешным только с проверенным парным `.dump.json`; хранить и защищать оба. Манифест содержит контрольную сумму, версии и точные применённые байты миграций. Прерванные `.partial` не принимаются за копии и не участвуют в хранении семи успешных комплектов. Блокировка операции принадлежит ОС и освобождается при завершении/аварии процесса; поддерживаются Windows и Linux. При обновлении со старого файлового механизма сначала остановить все старые процессы и задания: одновременно смешивать два механизма нельзя. Старые `.lock` автоматически не удаляются и больше не определяют владение. Удалять вручную можно только точный устаревший файл после проверки остановки старых процессов, без очистки всего каталога.

## Восстановление

1. Проверить происхождение архива, его контрольную сумму, манифест, версию PostgreSQL, выбранную схему и совместимую версию кода.
2. Подготовить другую пустую базу. Проверка учитывает также посторонние схемы; исходная база никогда не служит целью восстановления. Очистка или перезапись существующей базы не является обычным сценарием.
3. Восстановить ту же схему транзакционно, без владельцев/ACL исходного сервера. Сохранить статусы, версии, поколения расписания, lease/claim, обработанные события и историю.
4. Сравнить данные, ключевые связи, снимки, очереди и ledger. Восстановленная база остаётся без Worker, Telegram-секретов, webhook, cron и фонового отправителя.
5. Переключение работающего бота выполняется отдельно: остановить прежнего отправителя, проверить просроченную работу и совместимость кода, восстановить следующее пробуждение, затем явно включить доставку.

Дополнительно задать `RESTORE_DATABASE_URL` другой пустой базы и `RESTORE_ARCHIVE` — абсолютный путь конкретного доверенного `.dump` в `BACKUP_DIR`, затем выполнить `pwsh -NoProfile -File scripts/restore.ps1`. Скрипт не выбирает «последнюю» копию автоматически. Успех: код 0, `ok:true,restored:true`; отказ: код 1 и фиксированный `RESTORE_FAILED`. Исходная база может быть недоступна: `BACKUP_DATABASE_URL` нужен для проверки её прежней идентичности, рабочие учётные данные источника для restore не требуются. Архив должен происходить из доверенного хранилища; контрольная сумма не заменяет доверие к его содержимому.

Копия PostgreSQL не содержит состояние Durable Object и его alarm. Обычная проверка cron может восстановить alarm из существующего состояния DO, но не вычисляет срок для нового пустого DO по восстановленной базе. Успешный SQL-restore не означает, что работающий сервис уже переключён.

Для исторической миграции 002 в старой тестовой схеме применены CRLF-байты, отличные от LF в Git при одинаковом SQL. Применённые миграции и ledger не переписываются. Точные исходные байты и суммы должны сохраняться с резервной копией; при восстановлении совместимого нового checkout проверяются именно они. Откат Git сам по себе не откатывает данные.

## Ограничения текущей проверки

Первое упражнение использует отдельные базы с вымышленными Telegram-ID и контактами. Оно не является регулярной копией работающей схемы бота. Реальные показатели CPU, задержек и потребления Neon фиксируются с периодом наблюдения и размером выборки; месячный расход остаётся оценкой. Автоматическая отправка старой очереди при восстановлении не запускается.
