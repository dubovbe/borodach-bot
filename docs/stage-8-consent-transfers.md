# Этап 8: переносы с согласием

Статус: реализация, затронутые PostgreSQL-проверки и независимое ревью пройдены; готовятся публикация и ручная приёмка. Этап согласован пользователем 2026-11-07 после завершённого этапа 7. База — 05cd871, ветка feat/stage-8-consent-transfers. Основа — [согласованное описание](superpowers/specs/2026-11-05-borodach-bot-design.md) и [этап 8 плана](superpowers/plans/2026-11-06-borodach-bot.md).

## Поведение

Клиент запрашивает другое время своей подтверждённой записи, мастер принимает или отклоняет запрос. Мастер или админ может предложить перенос; для клиента с Telegram требуется его согласие. Для ручного клиента без связи с ботом сотрудник фиксирует согласование по телефону с исполнителем, временем и способом согласия.

Пока предложение ожидает ответа, прежний визит действует, новое время временно занято. Принятие атомарно меняет время; отказ и истечение сохраняют прежнюю запись и освобождают новый интервал. Отмена визита закрывает ожидающий перенос. Состав услуг, стоимость и длительность сохраняются.

## Границы

Для запроса клиента действуют минимум два часа и открытый горизонт записи; сотрудник использует согласованные правила ручной записи. Срок ответа ограничен правилом инициатора и началом обоих визитов. Решение после срока запрещено независимо от своевременности фонового задания.

Прежний и предложенный интервалы одного визита могут пересекаться между собой; чужие записи и блокировки пересекать нельзя. На визит допускается один ожидающий перенос, клиентский запрос учитывается в его лимите одной ожидающей заявки. При изменении графика проверяются оба интервала. После успешного переноса старые напоминания аннулируются, новые планируются для подтверждённого времени.

## Реализация и проверка

Команда — Backend Architect Sol Medium и независимый Code Reviewer Sol High. До реализации проверяются стыки версий, прав, отдельных кнопок согласия, привязки ручного клиента и очереди напоминаний. Используются существующие транзакция shop-lock, время PostgreSQL, очередь и планировщик.

Проверки охватывают отказ/истечение, согласие на границе срока, одновременную отмену и принятие, повторное согласие, собственное пересечение старого/нового времени и запрет чужой брони. Отдельно проверяются права и история телефонного согласования, неизменность снимков услуг и отсутствие отправок устаревших напоминаний.

Полный регрессионный набор выполняется в GitHub CI с PostgreSQL 17; изменённые SQL-сценарии — в отдельных собственных схемах Neon. Текущий тестовый Worker, профиль помощника, отменённый визит этапа 7 и прежние preview сохраняются. Для ручной приёмки переноса будет использован новый вымышленный визит. Этапы 9–11 не начинаются автоматически.

## Решения предварительной проверки

Совмещение ролей не заменяет согласие второй стороны. Обычное Telegram-согласие не может дать тот же пользователь, который создал предложение; актуальные полномочия обеих сторон проверяются при принятии. Телефонное согласование остаётся явным исключением только для ручного клиента, который по-прежнему не связан с Telegram.

Если ручной клиент подключает Telegram во время ожидающего предложения, прежнее предложение закрывается вместе с его временной блокировкой. Сама запись сохраняется и привязывается клиенту; для переноса потребуется новое предложение. Это исключает автоматическое согласие и использование старой телефонной кнопки после привязки.

Для состояния переноса и кнопок согласия предусмотрена дополнительная миграция 005. Отдельное поколение расписания отличает изменение времени от смены владельца записи. При возврате A → B → A напоминания планируются для нового подтверждённого переноса; смена телефона сама по себе не повторяет уже отправленное.

Миграция отказывается выполняться при неизвестном ожидающем переносе старой версии, сохраняя прежнюю схему и данные. Терминальная история переносов сохраняется без вымышленных авторов. После использования новых переносов возврат старого приложения требует совместимости с поколениями расписания; безопасный путь — совместимое исправление с сохранением дополнительных полей и истории. Автоматическое удаление полей и восстановление данных поверх новых действий не предусмотрены.

## Проверки реализации

Локально прошли 75 unit-тестов, 72 Worker-теста и 3 Node-проверки; типы и dry-run сборка успешны. Основной агент отдельно повторил проверку типов и сборку зафиксированных исходников: 685,48 KiB, gzip 155,90 KiB. Новых зависимостей нет. Проверка 100 версионируемых файлов по восьми локальным секретным значениям не обнаружила совпадений.

На Neon первоначальный отрицательный запуск подтвердил отсутствие команд переноса: три ожидаемых отказа вместо pending после успешного создания старых визитов. После реализации полный выбранный набор прошёл 17/17 за 513,12 с: 15 сценариев переносов, upgrade/guard 005 и прежняя проверка миграций. Четыре затронутых прежних сценария отдельно прошли за 94,02 с: отмена при открытом переносе, привязка ручного визита с историей напоминаний, исторический cutoff/ожидающая доставка и лимит заявок между мастерами.

Проверены собственное пересечение интервалов и запрет чужого, неизменность архивных услуг/цены/длительности, сохранение старых напоминаний до согласия, гонки двух решений и отмены, границы срока, клиентские ограничения и исключения сотрудников. Телефонное согласие и отмена предложения при привязке проверяются через защищённую identity-операцию, включая прямой вызов. Переход A → B → A использует последовательные реальные моменты: после отправленного прежнего напоминания новое поколение получает будущий запасной час.

Независимое ревью выявило три исправления: канонический LF-файл новой миграции и проверки актуальности автора/результата в очереди. Для них новые Worker-проверки сначала дали 10 смысловых падений при трёх положительных случаях, затем прошли 13/13. Повторное ревью требований и качества — PASS. Смена ролей запрещает устаревшее принятие, сохраняя безопасный отказ; отложенное подтверждение прежнего переноса подавляется после следующего переноса или отмены. Актуальные результаты при смене только владельца и уведомления о закрытии после привязки сохраняются.

Итоговый PostgreSQL-запуск исправлений проверил пять новых сценариев доставки и две миграции: шесть прошли, один сценарий остановился на существующем секундном пределе закрытия соединения (`Database close timeout`). Изолированный повтор того же сценария прошёл за 35,48 с без изменения кода или лимитов. Первоначальная ошибка сохранена; её причина не объявляется устранённой. Все затронутые проверки данных выполнены, полный регрессионный набор ожидается в GitHub CI.

Миграции 001–004 неизменны. Новая 005 имеет LF и SHA-256 `054c3f5b0d0f628c46c78e7fafde3074a3c2145e59d51a69dbc6d36e3ea52e8f`; перед сохраняемым обновлением проверяется совпадение реальных байтов с committed Git blob. Рабочая тестовая схема пока остаётся на этапе 7. После CI предусмотрены приватный снимок данных, транзакционная миграция 005, обновление прежнего тестового Worker и ручная проверка двумя аккаунтами. История отменённого визита этапа 7 сохраняется; этап 9 не начинается.
