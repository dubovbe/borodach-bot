## Подтверждение контакта

Бот принимает только свой контакт из приватного сообщения: user_id обязателен и совпадает с отправителем. Ввод цифр текстом не подтверждает телефон. [Кнопка request_contact](https://core.telegram.org/bots/api#keyboardbutton) предназначена для личного чата. Это номер Telegram-аккаунта, а не SMS-подтверждение текущей SIM.

Храним канонический E.164. Ручные номера разбираются с RU по умолчанию, цифры контакта Telegram — как международный номер. Невалидные номера и добавочные отклоняются. Конфликт чужого активного номера не меняет старое владение или профиль. История claims сохраняется при смене номера.

Только при первом успешном подтверждении связываются будущие confirmed ручные визиты с соответствующим нормализованным номером и user_id IS NULL у ручного клиента. Переносится подходящий визит, а не вся клиентская карточка: прошедшая история не открывается новому пользователю. Записи связанных клиентов и последующие смены номера не переносят владение. Перед записью backend проверяет активную привязку номера и заполненное имя; получение телефона не заменяет ввод имени этапа 6.

## Права

Роли накапливаются. Неизвестные действия и отсутствующий обязательный ресурс запрещены по умолчанию. Клиент получает только свои данные, барбер — только свой действующий профиль и рабочие данные; админ имеет права в рамках известных действий. Передача двух ID не должна разрешать чужой ресурс через независимое OR. Первый админ назначается только по первоначальной конфигурации.

## Одноразовые ссылки

Выдача и отзыв доступны админу. Приглашение живёт 24 часа по времени PostgreSQL, применяется один раз и связывает только активного свободного барбера. Новый барбер не получает роль админа. Одновременное использование и повтор одного update проверяются транзакционно.

Токен детерминированно восстанавливается через HMAC-SHA256 отдельного INVITATION_SECRET и UUID приглашения. В invitations хранится только SHA-256 токена; очередь хранит ID, processed_updates/result/audit не содержат открытой ссылки. Renderer строит ссылку перед отправкой после повторной проверки статуса и прав адресата. Секрет должен быть стабильным, задаётся локально и не попадает в Git. Параметр i_ с 43-символьным токеном укладывается в [лимит Telegram в 64 символа](https://core.telegram.org/bots/features#deep-linking).

Отзыв, замена и использование приглашения должны атомарно отменять его неотправленные сообщения и очищать lease/claim. Поздний ответ провайдера тогда не возвращает сообщение в очередь и не меняет его статус. Уже начавшийся HTTP-запрос к Telegram отозвать нельзя; полученная после отзыва ссылка всё равно не даёт привязать профиль.

Локальный отдельный случайный секрет подготовлен в игнорируемом .dev.vars без вывода значения. В Cloudflare на этом этапе он не загружается. Для будущей публикации нужен этот же стабильный секрет: смена ключа нарушит восстановление ранее созданных ссылок, поэтому её нельзя делать как обычный перезапуск.

## Границы и проверка

UI этапа ограничен запросом собственного контакта и приёмом /start i_…; календарь и административные экраны остаются следующим этапам. Отправки идут через outbox, сохраняются проверки secret/health, lease/fencing и повторы этапа4. Работающий Worker и preview этапа4 не обновляются.

Тесты используют случайные собственные схемы существующей изолированной Neon-ветки stage2-integration. Сохранённая preview-схема этапа4 и public не очищаются. Применённые миграции001/002 не переписываются; новая003 добавляется только при необходимости, с проверкой checksum/повторного запуска. Откат кода не отменяет данные; автоматического destructive down нет.

После восстановления с выключенного компьютера основной агент повторно выполнил `npm test`, `npm run typecheck`, `npm run build`: 38 unit, 32 Worker и 3 CLI теста прошли; TypeScript и dry-run сборка завершились с кодом 0. Размер сборки: 603,49 KiB, gzip 138,35 KiB. Развёртывания не было.

Независимый Code Reviewer на Sol High одобрил весь этап, включая отмену приглашений и последующее исправление порядка проверки роли: подтверждённых Critical/Important замечаний нет. Успешный результат прерванного выключением процесса не предполагается. Журналы повторных проверок сохраняются локально в игнорируемой .wrangler. Этапы 6–11 не начаты.

Полный повторный прогон Neon: 51 PASS и 2 FAIL из 53 сценариев за 802,52 секунды. Контакты/права/приглашения (14), outbox (16), транзакции (11) и upgrade (1) прошли. В бронировании исправлен порядок проверки: отсутствие роли клиента даёт forbidden до проверки профиля; клиенту с незаполненным профилем по-прежнему возвращается profile_required. После этой единственной правки кода повторены все 11 сценариев бронирования: PASS за 173,18 секунды. Отдельно повторён изменённый сценарий identity с проверками полного/неполного профиля и роли: PASS за 38,36 секунды. Остальные группы не менялись и повторно через сеть не запускались; CI проверяет весь набор на PostgreSQL 17.

Итоговые команды: `npm test`, `npm run typecheck`, `npm run build`; для Neon — `node --env-file=.env.integration node_modules/vitest/vitest.mjs run --config vitest.integration.config.ts --testTimeout=60000`, затем после правки роли полный booking-races и identity с фильтром `-t 'booking refuses'`. Контрольные суммы подтвердили, что после первого полного прогона менялись только booking/service.ts и соответствующий сценарий identity. Повторные локальные 73 проверки и сборка прошли. Проверены 13 локальных ссылок документации, diff-check и отсутствие шести локальных секретных значений в 73 публикуемых файлах.

Другой FAIL был однократным 55P03 при ожидании shop lock в конкурентном запросе. Сравнение предыдущей версии и текущей в порядке ABBA на одинаковых данных: четыре гонки дали ровно один pending и один slot_unavailable, подтверждение и соседний визит прошли во всех четырёх повторах. Успешный request выполнял 31 SQL-запрос в обеих версиях; получение профиля с сетевым обменом занимало 79–88 мс раньше и 81–90 мс после изменения. Наблюдаемое удержание блокировки для успешного request: 2113–2308 мс раньше и 2163–2372 мс после изменения. Это локальные диагностические замеры через сеть, не гарантия задержки в Cloudflare. Устойчивую регрессию этапа 5 не подтвердили; точная причина исходного единичного таймаута не измерена. Таймауты не увеличены, автоматические ретраи тестов не добавлены.

Внешние проверки Neon используют отдельный бюджет сценария `--testTimeout=60000`: один сценарий выполняет много последовательных транзакций через сеть. Ограничения приложения сохранены: lock_timeout 3 секунды, statement_timeout 4 секунды, query_timeout 5 секунд. Это разные ограничения. В тестовой фикстуре отдельно очищаются outbox и jobs: отсутствие FK у outbox означает, что TRUNCATE пользователей с CASCADE недостаточно.

Текущий requirePermission при передаче одновременно barberId и clientId требует права на оба ресурса и существующую связь через визит. Такой вызов может отказать барберу для клиентской карточки его посетителя. Сейчас consumer этого составного запроса отсутствует; перед рабочим местом барбера в этапах 9–10 правило нужно уточнить по конкретному действию.

## Уточнение служебной подсказки

Для группы сохраняется требование показать переход в личный чат. Это узкое исключение для общей подсказки без бизнес-изменений: best-effort ответ, без обращения к Repository/БД/DO, без номера/имени/содержимого контакта. Ошибка такой подсказки не запускает повтор бизнес-действия. Приватные изменения и ответы продолжают проходить через транзакцию и outbox.
